# Local adapter store and run records

The identity of a LoRA is the sha256 of its directory contents. That one
identity is used on all three surfaces:

```text
  adapter bytes
       |
       |  digest_of_tree  ->  sha256:abc...
       |
       +---> synth-mlx-rl   policy_snapshot_id   the proxy pins this per request
       +---> optimizers     artifact_digest      what eval scored, in its manifest
       +---> local store    adapters/sha256-abc  where the bytes live
```

Verified to agree across repos: `synth_mlx_rl.store.digest_of_tree` and
`synth_optimizers.eval.models.digest_of_tree` return the same digest for the
same directory. `tests/test_store.py` pins the algorithm against a
hand-computed vector rather than a golden file, because a golden file gets
regenerated by whoever broke it.

## Layout

```text
  ~/.synth/mlx-rl/
    store.toml                     root, retention. TOML, never an env var.

    adapters/sha256-<hex>/         immutable, read-only
        adapter_config.json
        adapters.safetensors
        policy.json                base model, rank, template digest, thinking mode
        provenance.json            run_id, step, parent_digest, algorithm, created_at

    runs/<run_id>/
        run.json                   base model, algorithm, config, dataset digest,
                                   seed, git revision, resumable
        events.jsonl               append-only
        checkpoints.jsonl          {step, adapter_digest, metrics}
        evals.jsonl                {eval_run_id, adapter_digest, scorecard_ref}
```

## Why it is shaped this way

**Digest-keyed, not name-keyed.** The upstream prototype wrote
`checkpoints/<name>/` from `save_state("experiment-0042")`. A caller-supplied
name is exactly how provenance is lost: two runs can reuse one, and a name
cannot verify the bytes it points at. Re-putting identical bytes is a no-op
that returns the existing record, so a warm start re-registering its starting
adapter neither fails nor stores a second copy.

**A run references adapters; it does not own them.** `checkpoints.jsonl` holds
`(step, adapter_digest)` pointers. Two runs starting from one adapter share its
entry.

**`parent_digest` gives lineage, not just parentage.** base -> SFT -> RL is a
reconstructible chain. Recording only `run_id` answers one hop and loses the
ancestry — which is the question actually asked when a number looks wrong.
`lineage()` terminates on a repeated digest rather than raising, because a
malformed provenance file is not a reason to make a stored adapter unreadable.

**The loop closes both ways.** A scorecard resolves to a run through
`runs_for_adapter()`; a run resolves to every eval that scored it through
`evals.jsonl`.

**An incomplete adapter is refused.** A directory missing
`adapters.safetensors` cannot be stored. Otherwise a checkpoint whose weights
failed to copy is storable as though complete, and would later be scored as
its own baseline.

**Configuration is TOML, never an environment variable.** A path that lives in
the environment cannot be read back off a finished run, which is the entire
reason a run record exists.

## Resumability is stated, not implied

The engine persists neither the MLX RNG state nor outstanding accumulated
gradients. `run.json` therefore carries `resumable: false` unless a caller
explicitly sets otherwise. A layout that looks resumable but is not is worse
than one that says so.

## Relationship to the eval candidate store

Optimizers `eval` requires candidate contents mounted read-only from
`<eval-home>/candidates/<id>/`, so staging copies the adapter in. That is
correct rather than duplication: a few MB, and the shared digest makes the copy
checkable against this store.
